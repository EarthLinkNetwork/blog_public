# AWSの小さな課金を、100倍になった時を想像して下げた

2026 年 6 月、AWS 請求を見直し始めました。狙いは、今月の請求をいくら削るかではありません。いま数ドルの小さな課金でも、利用が 100 倍になれば固定費として重く効いてきます。その「将来の額」を先に想像して、動かしながら直し、身の丈に合ったインフラへ寄せていく。これはその実測記録です。

先に分かったのは、一番お金を食っているのは本体機能ではない、という事実でした。食っていたのは、CDK(コードで AWS 構成を定義するツール)が勝手に立てた NAT Gateway(プライベート網から外部へ出るための中継。立てっぱなしで課金される)、ビルドしているだけの Amplify(AWS のビルド・ホスティング基盤)、15 分ごとに走る稼働確認の Lambda(イベントで起動する関数実行基盤)、そして誰も見ていない dev(開発)環境に溜まった 82 万件のゴミデータでした。どれも、今は小さいか、気づかない課金です。でも放っておくと、利用や時間に比例して伸びていきます。だから「100 倍になったらどうなるか」で見て、順に潰しました。

結論を先に置きます(本文の読了は約 11 分)。

- **一番高い固定費は本体機能ではなく、IaC(インフラをコードで定義する手法)のデフォルトが勝手に立てた NAT Gateway だった** — `natGateways` を明示しないと AZ(アベイラビリティゾーン。データセンターの区画)ごとに 2 基立ち、月 $58〜66 かかっていた。「サーバーレスだから固定費ゼロ」は自動では成立しない
- **Amplify 請求の 87〜89% は「ビルド時間」だった** — 実測で内訳を割ると、移すべきは runtime(月 $3〜7)ではなくビルドそのもの。git 連携の自動ビルドを止め、1 回作った成果物を昇格させる形へ切り替えた
- **月 $47 の DynamoDB(AWS の NoSQL データベース)読み取りは、監視 Lambda 自身が生んでいた** — 15 分ごとに 1.22GB の索引を全件数え直していた。データが増えるほど比例して伸びる、放置できないコストだった
- **可視化そのものが 100 倍間違えることもある** — コストダッシュボードが、あるプロバイダの料金を 100 倍に膨らませて表示していた。数字で判断するなら、その数字が正しいかをまず疑う

私のポートフォリオの請求は、ほぼ 1 つのニュースキュレーション基盤に集中していて、他のプロダクト(静的サイトや小さな SaaS(サービスとして提供されるソフトウェア))は月数ドル以下でした。だからこそ「本体以外」を先に潰すのが効きました。以下、何を測り、どう直したかを、将来の額で見る目線とあわせて残します。

## 戦線 1: CDK が勝手に作った NAT Gateway 2 基、月 $64

最初に見つかった大きな固定費は、稼働監視 SaaS の方にありました。ブラウザ監視を ECS Fargate(サーバー管理不要のコンテナ実行基盤)で動かすスタックで、CDK に VPC(仮想プライベートネットワーク)を明示していなかったため、**暗黙 VPC が自動生成され、AZ ごとに NAT Gateway が計 2 基**立っていたのです。これが月 $58〜66。dev 専用ワークロードの Lambda と DynamoDB を全部足した額より、この固定費の方が高いという逆転が起きていました。「固定費ゼロのサーバーレス」を掲げた設計が、フレームワークのデフォルトに裏切られていた形です。

IP allowlist(接続元 IP を限定する運用)もしておらず、NAT の固定出口 IP に価値はありませんでした。そこで VPC を明示し、NAT を明確にゼロにして、public subnet(外部から直接到達できるネットワーク区画)からの直接 egress(外向き通信)へ変えました。

```ts
// 暗黙 VPC に NAT を勝手に立てさせない。ゼロを明示する
const vpc = new ec2.Vpc(this, "MonitorVpc", {
  natGateways: 0,
  subnetConfiguration: [
    { name: "public", subnetType: ec2.SubnetType.PUBLIC },
  ],
});
// Fargate タスクは public subnet + パブリック IP で外に出る
new ecs.FargateService(this, "BrowserWorker", {
  cluster,
  assignPublicIp: true,
  vpcSubnets: { subnetType: ec2.SubnetType.PUBLIC },
});
```

これだけで月 $58〜66 が消えました。金額としては小さく見えるかもしれません。でも NAT は「立っているだけで課金される」固定費で、AZ やプロダクトを増やすほど基数が増えて比例して伸びます。今 $64 でも、構成が 100 倍に育てば、そのまま重い固定費になる。だから小さいうちに、明示的にゼロへ倒しました。教訓は単純です。**サーバーレスだから固定費ゼロは、自動では成立しない**。IaC のデフォルトが何を立てるかまで見ないと、掲げた設計原則が裏で破られます。

## 戦線 2: Amplify 請求の 87% は「ビルド時間」だった

次はデプロイ基盤です。CI/CD(変更のたびに自動でテストしデプロイする仕組み)の自作ポータルでコストを可視化していて、Amplify の請求を Cost Explorer(AWS の費用内訳を分析するツール)で内訳分解したところ、**月次請求の 87〜89% が `BuildDuration`**、つまりビルドに費やした時間で、実際のランタイム(SSR(サーバー側で HTML を生成する方式)ホスティング)はわずか月 $3〜7 でした。6 月は一時 $60 台に跳ねています。

当初の計画は「SSR を別基盤へ移設する」でしたが、それはコストの 11% 側を触る話でした。実測が戦略を反転させます。触るべきは 89% 側、すなわち**ビルドそのものを止める**こと。git 連携の自動ビルドを停止し、自前の CI ランナーでビルドした成果物だけをデプロイする「build once, promote many(1 回作って各環境へ昇格させる)」に切り替えました。1 回ビルドした成果物を dev→staging→prod へ昇格させるので、Amplify 上のビルドは基本ゼロになります。ビルドは開発が活発になるほど回数が増える側なので、今の額が小さくても、将来は比例して伸びます。だから移設ではなく、丸ごと止めました。

ここで 1 つ、プラットフォーム固有の壁に当たりました。git 連携済みの Amplify アプリは、成果物を直接送り込む `create-deployment` API(成果物を直接アップロードしてデプロイする API)を拒否するのです。既存アプリの設定変更では逃げられず、環境ごとに repo 未連携の「手動デプロイ専用アプリ」を新設して回避しました。

## 戦線 3: 月 $47 の原因は「15 分ごとの稼働確認」

3 つ目が、15 分ごとの monitor(監視)です。キュレーション基盤の DynamoDB 読み取りコストが月 $47 に達していて、内訳を追うと本体機能ではなく、**パイプラインの健康状態を監視する Lambda が 15 分ごとに 1.22GB の GSI(グローバルセカンダリインデックス。検索用の副次索引)を全ステータス分 COUNT(全件を数える走査)していた**ことが原因でした。しかもその大半は、一度終端に落ちたらもう変化しない除外系ステータス(パースエラーや anti-bot(ボット除け)による除外)まで毎回数え直していた。**監視そのものがコスト源**という典型です。

応急処置は、ほぼ変化しない終端ステータスの集計頻度を落とすことでした。

```python
# 全ステータスを 15 分毎に COUNT していたのをやめ、
# 変化しうるものだけ高頻度、終端系は 2 時間毎に間引く
ACTIVE = {"RAW", "CRAWLED", "ANALYZING"}          # 動くもの
TERMINAL = {"EXCLUDED_PARSE_ERROR", "EXCLUDED_ANTIBOT", "PUBLISHED"}

def collect_counts(now):
    statuses = ACTIVE.copy()
    if now.minute < 15 and now.hour % 2 == 0:      # 終端系は 2h に 1 回だけ
        statuses |= TERMINAL
    return {s: count_by_status(s) for s in statuses}
```

これで読み取りコストは約 87% 減(月 $47 → $5〜6 相当)になりました。ただしこれは応急処置です。この設計のこわいところは、記事が増えるほど COUNT の対象も増え、コストがデータ量に比例して伸びる点にあります。今 $47 でも、扱う記事が 100 倍になれば読み取りもおよそ 100 倍。だから恒久解として、ステータス集計を毎回 GSI で数えるのをやめ、DynamoDB Streams(テーブルの変更を逐次流すしくみ)で件数を差分更新する**カウンタテーブル**にして、集計の読み取りを O(1)(件数に関係なく一定の処理量)にしました。これは翌月に実装しています。「周期的に全部数える」設計は、根っこから消す価値があります。

## 戦線 4: 監視・バックアップ・dev 環境という「本体以外」

戦線を重ねて見えてきたのは、コスト源がどれも決まって「本体以外」に集まることでした。バックアップエンジンが毎日 dev テーブルをフルスキャンしていて、そこに溜まった **82 万件超のクロールジョブ痕跡・記事ゴミ**が、そのままスキャン量とバックアップ量を押し上げていた。dev を運用系の 665 件までパージして解消しました。小さなゴミも、82 万件たまれば毎日のスキャン費になります。稼働監視 SaaS 側でも、dev の 22 モニターを 5 分間隔から日次に落として月 $18→$4 に、prod の詳細コンテナメトリクスを無効化して CloudWatch(AWS の監視・メトリクス基盤)費を削りました。取り込み前トリアージで分析対象を約 94% 減らし、1 日あたりの分析コストを $0.13 に抑えたのもこの流れです。

横断で効いたのが、複数プロバイダのコストを 1 画面に集めるダッシュボードでした。ここで笑えないバグにも当たりました。ある日 Anthropic のコストだけ異様に大きく表示され、調べると **Admin API(Anthropic の管理用 API)はコストをセント建て(最小単位)で返す**のに、スクリプトがドルとして合算していた。API の生値 `"58.3135"` は $0.58 が正しく、100 倍に膨れていたのです。÷100 の 2 行修正で直りましたが、教訓として「3 プロバイダで通貨単位が全部違う(一方はセント、一方はドル、請求は円)」をメモに残しました。将来の額を想像するには、まず今の数字が正しく見えていることが前提です。可視化が 100 倍間違っていたら、コスト判断はまるごと狂います。

## 仕組み: なぜ「本体以外」が将来のコストになるのか

やってみて腑に落ちたのは、コストの出やすい場所には共通構造があるということです。**本体機能はリクエストが来たときだけ課金される (弾力的) のに対し、NAT・ビルド・周期監視・バックアップは「動いていなくても・変化がなくても走り続ける」定常コスト**だからです。定常コストは、規模や時間、データ量に比例して静かに伸びます。しかもこれらは IaC のデフォルトや「とりあえず 15 分間隔」のような無意識の設定として紛れ込むので、機能開発の視界に入りません。だから「今いくらか」ではなく「100 倍になったらいくらか」で見る。そのうえで「測ってから直す・直したら測る」を運用に固定し、コスト変化を請求ではなくダッシュボードで日次に見るようにしました。請求書は 1 か月遅れてやってくるので、それだけを見ていると手遅れになります。適切なインフラとは、機能が動くことではなく、この定常コストが将来も破綻しない形に整えることでした。

## まとめ — 転用できる教訓

- **今の額ではなく「100 倍になったら」で見る**。小さい定常コストほど、規模やデータ量に比例して静かに伸びる。小さいうちに、伸びる構造ごと消す
- **IaC のデフォルトを疑う**。`natGateways` を明示しないと NAT が勝手に立つ。「サーバーレス＝固定費ゼロ」は自動では成立しない
- **請求は内訳を分解してから直す**。Amplify の 87% がビルド時間と分かって初めて、11% 側の移設ではなく 89% 側の停止が正解だと分かった
- **周期実行は増えるほど高くつく**。15 分ごとの全 COUNT は差分カウンタで O(1) に。監視・バックアップ自身がコスト源になり得ると疑う
- **可視化を正しく作る**。プロバイダごとに通貨単位が違う。ダッシュボードが 100 倍間違えていたら、将来の額どころか今の判断ごと狂う
